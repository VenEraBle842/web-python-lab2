## Вопрос 3. Почему async, await и asyncio.run не ускорили программу

В шаге 2а цикл выполняет `await work(n)` и ждёт, пока текущая корутина
полностью завершится. Только после этого начинается следующая итерация.
Поэтому десять ожиданий по одной секунде по-прежнему складываются примерно
в десять секунд: `await` подряд — это последовательное выполнение.

Внутри `work` выражение `await asyncio.sleep(1)` приостанавливает выполнение
корутины и позволяет циклу событий выполнять другие готовые задачи.
Но в варианте 2а остальные вызовы `work` ещё даже не созданы и не запланированы.
Циклу событий нечего выполнять из нашей работы до окончания текущего ожидания.
Само наличие `async` не запускает несколько задач одновременно.

Решение шага 2а сохранено в функции `main_sequential` файла `step2_async.py`.
Обычный запуск этого файла выполняет итоговый конкурентный вариант шага 2б.

## Вопрос 5. Что возвращает вызов work(n) без await

Вызов функции, объявленной через `async def`, создаёт объект корутины.
Он не исполняет её тело и не планирует её выполнение автоматически.
Поэтому после удаления `await` строки `start` и `done` не появляются,
а программа заканчивается практически сразу.

При эксперименте с `print(work(n))` вывод имеет вид:

```text
<coroutine object work at 0x...>
```

Здесь `0x...` обозначает адрес объекта; конкретные адреса могут отличаться.
В цикле из десяти вызовов печатаются десять таких объектов. При уничтожении
объектов корутин Python сообщает, что их никто не ожидал:

```text
RuntimeWarning: coroutine 'work' was never awaited
```

Предупреждение выводится в стандартный поток ошибок. Количество его
повторений зависит от фильтра предупреждений. Для одного и того же места
вызова стандартный фильтр обычно показывает его один раз.

Чтобы выполнить корутину, можно ожидать её через `await`, передать её
в `asyncio.gather` или создать из неё задачу через `asyncio.create_task`.
В итоговом решении ожидание восстановлено; неправильный вариант использовался
только в отдельном проверочном запуске.

## Вопрос 6. Почему сначала выводятся все start, затем все done

В шаге 2б список содержит десять объектов корутин. `asyncio.gather(*coroutines)`
планирует их как задачи, а `main` ожидает общий результат.

Цикл событий запускает первую задачу. Она печатает `start 1`, доходит до
`await asyncio.sleep(1)` и добровольно уступает управление. Ожидание таймера
не блокирует поток. Пока первая задача приостановлена, цикл событий запускает
следующую: она печатает `start 2` и тоже приостанавливается на своём ожидании.
Это повторяется для всех десяти задач, поэтому сначала видны все строки `start`.

Примерно через секунду таймеры срабатывают, задачи становятся готовыми
к продолжению и по очереди печатают `done`. Все ожидания перекрываются
по времени, поэтому общее время близко к одной секунде, а не к десяти.
В этом примере задачи выполняются в одном потоке; параллельные вычисления
на нескольких ядрах не используются.

Порядок `done 1` … `done 10` наблюдался при проверке. В общем случае порядок
завершения конкурентных задач определяется их готовностью: `gather` сохраняет
порядок возвращаемых результатов, но не гарантирует порядок печати внутри задач.

## Вопрос 8. Когда получают ответ alice и carol в синхронном сервере

`alice` получает ответ примерно на отметке **0,5 с**. После неё сервер
обрабатывает `bob` ещё 5 секунд. Поэтому запрос `carol` принимается только
на отметке **5,5 с**, а ответ отправляется на отметке **6,0 с**.

Из шести секунд ожидания `carol` только последние 0,5 секунды приходятся
на её собственную обработку. Остальные **5,5 секунды** она ждёт чужие запросы:
0,5 секунды для `alice` и 5 секунд для `bob`.
В эмуляции все клиенты заданы заранее, но последовательный цикл добирается
до обработчика `carol` только после завершения `bob`.

## Вопрос 11. Что сэкономила асинхронность, если bob всё равно нужны 5 секунд

В синхронной версии `bob` сначала ждёт завершения `alice` 0,5 секунды,
затем обрабатывается 5 секунд и получает ответ на отметке 5,5 секунды.
В асинхронной версии его обработка начинается почти сразу, поэтому ответ
приходит примерно на отметке 5,0 секунды. Сэкономлено ожидание своей очереди,
а сама обработка по-прежнему длится 5 секунд.

Для остальных клиентов эффект заметнее: их обработчики запускаются сразу,
и `alice`, `carol`, `dave`, `eve` получают ответы примерно через 0,5 секунды.
В частности, `carol` больше не ждёт 5,5 секунды перед началом своей обработки.
Общее время обслуживания всех клиентов сокращается примерно с 7 до 5 секунд:
вместо суммы ожиданий получается время самого долгого из них.

**Асинхронность борется с простоем и ожиданием очереди во время чужого
I/O-ожидания, позволяя обслуживать другие задачи; длительность самой операции
и долгие вычисления она не сокращает.** В этой работе ожидание базы данных
эмулируется через `sleep`, реальные сетевые запросы не выполняются.

## Запуск

Нужен Python 3.10 или новее. Сторонних библиотек нет.
Из корня проекта:

```bash
cd starter
python3 step1_sync.py
python3 step2_async.py
python3 step3_server.py
python3 step3_server_async.py
```

Чтобы отдельно запустить сохранённый шаг 2а, из каталога `starter`:

```bash
python3 - <<'PY'
import asyncio
from step2_async import main_sequential
from timer import print_time

with print_time():
    asyncio.run(main_sequential())
PY
```

Время немного зависит от планировщика операционной системы. Проверяются
порядок сообщений и близость времени к ожидаемому, а не точное совпадение
сотых долей секунды.
